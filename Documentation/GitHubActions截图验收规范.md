# 视觉 Review 与 GitHub Actions 验收规范

## 当前原则（2026-09-21 更新）

视觉验收不再要求每一轮修改都等待 GitHub Actions。

日常美术／服装迭代优先采用“修改 → 本地或执行环境渲染 → 多角度截图 → 实际看图 → 继续修改”的短循环。GitHub Actions 保留为自动检查、动画／浏览器完整链路、关键里程碑和合并前兜底，不再承担每次视觉迭代的唯一截图来源。

必须区分三类证据：

1. **真实本地网页截图**：能启动 Vite / Three.js 时，直接打开当前代码运行结果，操作角色并截图。可用于静态外观、UI、相机、换装以及已成功载入的动画画面。
2. **源码几何重建截图**：当前角色、上衣、裤装、鞋和发型由源码确定性生成时，可以从当前 SHA 的源码参数重建静态绑定姿态并离线渲染正面／侧面／背面／三分之四等图片。它适合审查轮廓、裆部、衣裤接口、发型和比例，但**不能**代替网页 UI、WebGL 运行时、Mixamo 动画或连续穿模验证。
3. **GitHub Actions 产物**：用于完整依赖环境、FBX 扫描／重定向、Playwright 浏览器矩阵、自动贯穿检测、基线对照和最终回归。

交付时必须明确截图属于哪一类，不能把源码重建图写成浏览器实机截图，也不能把单张静态图写成连续动画已通过。

## 日常迭代流程

服饰轮廓、配色、头饰、发型、腰线、袖口、裤型、局部几何等高频调整，不必每次推送后等待 Actions。

推荐流程：

1. 读取最新 main 和任务相关文档，确认当前 SHA。
2. 修改代码并尽量执行当前环境可运行的本地检查。
3. 优先直接启动项目做本地浏览器 Review；若环境无法完整启动，但改动属于确定性的静态程序化几何，可使用源码几何重建截图。
4. 至少检查正面、侧面、背面和三分之四；涉及髋裆、袖口、帽子或头发时补近景。
5. 实际查看图片并记录发现的问题，继续迭代。
6. 当方案达到可验收状态，再统一跑必要的 GitHub Actions，而不是每个小提交都等待全套截图产物。

本地 Review 的目标是提高迭代速度，不是降低验收标准。

## 什么时候必须跑 GitHub Actions

以下情况仍应执行对应 Actions／自动检查：

- 准备把运行时代码、网格、绑定、换装或动画改动合入 main；
- 修改骨骼、权重、绑定矩阵、retarget、Mixamo 播放器或 FBX 处理；
- 修改自动贯穿算法、阈值、黄金数据、截图脚本、测试或工作流本身；
- 需要验证全部 FBX、源键／中点采样、循环／播放结束、Playwright 交互矩阵；
- 本地环境无法覆盖的 WebGL／浏览器问题；
- 建立或更新正式视觉基线；
- 发布、阶段收尾或用户明确要求完整 Actions 验收。

纯文档修改不需要重新跑代码 Actions。仅静态美术探索阶段可以先连续进行多轮本地 Review，在候选方案稳定后再集中跑一次相关 Actions。

## 自动检查与正式任务

两个固定成年男女基模，一种标准精度。全部 FBX 自动扫描，文件数不是固定上限。

本地环境可用时优先执行：

- `npm run check:retired`
- `npm run check:mesh`
- `npm run build`
- `npm run check:mixamo`
- `npm run check:wardrobe`
- `npm run check:tailoring`

正式 Actions 继续保留 Build、Character Model Review、Mixamo Retarget Review、Wardrobe Review、Tailoring V2 Review，以及 Modular Garment Review。它们是合并前和关键节点的自动化兜底，不要求每个美术微调提交都等待全部任务结束。

重点动作仍包括 Pilot Flips Switches、Shooting Arrow、Jogging、Snatch 和现有起步、行走、劳动动作。动画相关结论必须来自真实动画运行／自动采样，静态源码重建图不能替代。

## 图片审查要求

静态服装或人物轮廓至少检查：

- 正面；
- 侧面；
- 背面；
- 三分之四；
- 相关局部近景。

修髋裆时补浅色、无光照或线框定位；修头发／帽子时补头部侧面与背面；修袖子时补手臂抬起或动画关键姿态（若动画环境可用）。

Actions 的多相位图片、真实截图接触表、同相机前后对照仍保留。打开关键原图，记录原图精查、接触表抽样及未查看范围；不根据静态截图声称整个连续过程全部通过。

文件和交互继续检查 V5 往返、旧版与非法字段拒绝、错误导入不改变角色、旧存储隔离、退役控件清除、换装与性别切换保持相位、三色与发色、保存恢复、搜索收藏、暂停逐帧和小屏布局。

## 当前执行环境的边界

ChatGPT 的执行环境不保证每次都能联网安装 npm 依赖或提供可用的本地浏览器 CLI，因此不能假设每轮都能直接执行 `npm ci → npm run dev → 浏览器截图`。

当完整浏览器链路不可用，而待审内容是本项目当前的确定性程序化静态网格时，可以读取当前 GitHub SHA 的源码，在执行环境中重建并渲染静态角色截图用于美术判断。此方式已经用于验证模块化服装的静态多角度 Review 可行性。

但下列项目不得由这种静态重建方式冒充已验证：

- React 页面和交互；
- Three.js / WebGL 实际运行状态；
- Mixamo FBX 动画；
- 动画连续穿模；
- 播放结束／循环；
- 浏览器尺寸适配；
- Playwright 流程。

这些项目需要真实本地网页运行或 GitHub Actions。

## 版本、证据与交付

交付记录应包含：

- 审查所对应的代码 SHA；
- 本地检查／Actions 的真实状态；
- 使用的截图类型：本地网页、源码几何重建或 Actions artifact；
- 实际查看的角度、动作、相位和局部范围；
- 未覆盖的范围；
- 已知限制；
- 最终 main SHA。

原身体／绑定黄金数据保持；旧人体衣面 surfaceHash 已退役，新几何版本为 `wanhu-modular-garments-v6`。服装主导路线允许按明确覆盖表不绘制内部皮肤，但裤装自身必须连接完整。不得修改上传 FBX、删除失败动作、放宽阈值、临时删除可见衣面或调整照明来伪造通过。

自动检查通过不代表美术已经完成；本地截图看起来正常也不代表完整动画链路通过。两者各自负责不同层级的验证。

## 合并策略

高频美术阶段可以先通过多轮本地 Review 收敛，不需要为了每个中间状态反复等待 Actions。

准备合入 main 的运行时代码应按改动范围执行必要自动检查；涉及网格／换装／动画的正式阶段交付，至少保证相关 Actions 成功，并记录真实受测 SHA。仅文档变更可以直接更新文档而不重新跑视觉工作流。

用户最终仍可以拉取 main 做简单视觉复核；其目的不是代替前面的自动检查，而是确认最终美术观感。
