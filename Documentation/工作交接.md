# 工作交接

这是新对话、新 AI 或新开发者接手 Wanhu Character Lab 时的首要入口。

## 项目定位

本仓库用于验证《万户天工》的程序化人物生成方案。

它不是最终 Web 产品，也不是独立角色编辑器产品。最终目标是把验证稳定的规则迁移到 Unity，用于大规模城市居民。

网页主要验证：

- 人体参数如何映射为运行时 Mesh；
- 服装如何从 Recipe 生成而不是加载成品模型；
- 骨骼、蒙皮、LOD、合并和缓存策略；
- 角色数据协议是否能被 Web 与 Unity 同时理解。

## 当前技术栈

- React
- TypeScript
- Vite
- Three.js
- Vercel：仅用于在线观察

正式 Unity 方向：

- Unity 6
- MeshData
- Burst / Jobs
- Entities
- SkinnedMeshRenderer 或后续验证后的 GPU 变形路径

## 当前阶段

当前为 Phase 0：项目骨架与最小程序化人体。

当前只需要证明：

1. 页面正常运行；
2. 不加载 FBX / GLB 人物资产；
3. 身高、体型、肩宽可以驱动运行时几何生成；
4. 结果最终进入单个 Three.js Mesh；
5. UI、生成核心、场景渲染职责分离。

当前生成的人体是低成本占位体，不代表最终美术质量和最终拓扑结构。

## 当前明确不做

Phase 0 暂不做：

- 最终人体拓扑；
- Humanoid 骨骼；
- 蒙皮权重；
- 人脸；
- 发型；
- 帽子；
- 服装 Recipe；
- UV Atlas；
- 材质系统；
- LOD；
- Mesh Cache；
- Unity 导出。

这些内容按后续阶段逐项验证，不在项目初始化时一次性铺开。

## 核心规则

人体、衣服、裤子等正式方案默认走运行时生成。

仓库未来可以包含用于算法对照、测试或美术参考的资源，但不得悄悄退化成“每件衣服一个 FBX / GLB”的传统换装系统。

Web 与 Unity 的共享层是：

- 参数定义；
- Recipe；
- 拓扑语义；
- Region；
- Skeleton 语义；
- LOD 规则；
- Character Recipe JSON。

不是 Three.js 对象或 React 组件。

## 当前关键代码

- `src/App.tsx`：实验 UI 与参数状态；
- `src/character/types.ts`：稳定参数类型；
- `src/character/generateHumanoidGeometry.ts`：Phase 0 程序化人体占位生成；
- `src/scene/CharacterViewport.tsx`：Three.js 场景与预览；
- `src/styles.css`：当前实验台布局。

## 下一步建议

Phase 0 验证通过后，不急着加衣服。

优先进入 Phase 1：

- 从基础几何拼接改为 HumanTopologyBlueprint；
- 用 Ring / Section 生成连续的人体区域；
- 明确 Body Region；
- 为后续骨骼权重与服装生成建立稳定拓扑语义。
