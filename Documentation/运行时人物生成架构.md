# 运行时人物生成架构

## 1. 核心判断

正式角色不应被理解为一组 Mesh Asset。

角色应被理解为：

`Parameters + Recipe + Runtime Generator`

最终 Mesh 是运行时编译结果，可以被缓存，但不是内容制作的主要源数据。

## 2. 长期数据链

`ResidentAppearance`
-> `CharacterRecipe`
-> `Body / Garment / Accessory Generator`
-> `Topology + Vertex Attributes`
-> `Mesh Assembly`
-> `LOD`
-> `CharacterMeshKey`
-> `Mesh Cache`

颜色、皮肤色、布料色等尽量不进入几何 Hash。

## 3. Web 与 Unity 的对应关系

Web：

- Character Parameters：TypeScript 数据；
- Generator：纯生成逻辑；
- Geometry：Three.js BufferGeometry；
- Preview：Three.js Scene。

Unity：

- Character Parameters：IComponentData / Blob；
- Generator：Burst Jobs；
- Geometry：MeshData；
- Runtime：Entities / Renderer / Cache。

两端保持“语义一致”，不要求 API 一致。

## 4. Phase 0 实现

当前版本仅有四个身体参数：

- Height；
- Build；
- Shoulder Width；
- Head Scale。

生成器运行时创建头部、胸腹、骨盆、四肢等简化几何，并合并为一个 BufferGeometry。

这是架构验证，不是最终人体生成算法。

当前允许的缺陷：

- 身体区域之间存在重叠；
- 内部存在不可见面；
- 没有连续拓扑；
- 没有骨骼和蒙皮；
- UV 只是基础几何默认结果；
- 没有 Body Region。

## 5. Phase 1 目标

下一阶段应替换“基础几何拼接”为 HumanTopologyBlueprint。

建议核心概念：

- BodySection；
- Ring；
- JointPatch；
- BodyRegion；
- SectionProfile；
- LOD Sampling Rule。

例如躯干不是一块现成 Mesh，而是若干语义横截面：

`Pelvis -> Waist -> Rib -> Chest -> Shoulder`

每个截面描述：

- 高度；
- Width；
- Depth；
- Offset；
- Rotation；
- 顶点采样数。

这样胖瘦、肩宽、腰围等参数直接改变截面，而不是依赖 BlendShape。

## 6. 服装方向

服装不保存为最终 Mesh。

长期使用 GarmentRecipe，例如：

- 覆盖 Region；
- 衣长；
- 宽松度；
- 袖长；
- 袖宽；
- 领型；
- 下摆；
- Material Role；
- Body Hide Region。

生成器根据当前身体表面生成服装几何。

## 7. 大规模运行约束

不要默认“一居民一独立永久 Mesh”。

长期策略：

- 几何参数量化；
- 生成 CharacterMeshKey；
- Mesh Cache；
- 相同几何不同颜色共享 Mesh；
- LOD 直接按不同采样密度生成，不先生成高模再做运行时减面；
- 近景与远景骨骼复杂度分级。

## 8. 当前目录职责

`src/character/`

只放与角色参数和几何生成相关的核心逻辑，不依赖 React UI。

`src/scene/`

负责相机、灯光、Orbit、Renderer 和将生成结果显示出来。

`src/App.tsx`

负责实验参数状态和界面，不包含具体人体几何算法。

这个依赖方向在后续开发中应保持稳定。
