# 动物工作流

## 目标

《万户天工》的动物部分从“单个模型展示”逐步扩展为适合中国古代城市、村落、院落、城郊、山林和水域的动物资源体系。这个工作流只负责 Web Demo 中的作者模型、骨架／动画、LOD、预览、自动检查和视觉验收；正式 Unity ECS 行为、生产、繁殖、导航和生态模拟仍不在本仓库实现。

当前已经存在坐骑与家畜两条成熟链路。后续新增动物不为了统一而强行共用同一套骨架或生成器：每个物种保留自己的造型、绑定、动作和数值所有权；只有明确相同的播放、缓存、批次、相机和工作台能力才进入共享层。

## 后续制作顺序

用户已经授权后续动物按以下顺序推进：

1. **A1 山羊**
2. **A2 猴子**
3. **A3 绵羊**
4. **A4 鹿**
5. **A5 兔子**
6. **A6 鸟类**
7. **A7 鱼类**

默认按顺序逐阶段完成。每一阶段先完成作者模型、动作、LOD、检查和真实 WebGL 视觉验收，再进入下一阶段；只有用户明确要求时才并行制作。

计划 ID 只作为命名方向，不在未开始阶段提前写入运行时目录：

- 山羊：`goat_domestic`
- 猴子：`monkey_macaque`
- 绵羊：`sheep_domestic`
- 鹿：`deer_sika`
- 兔子：`rabbit_domestic`

正式 ID、颜色和具体品种在对应阶段开始前根据中国古代城市环境、现有美术比例和用户验收再最终确定。

## 系统分线

### 地面家畜

山羊、绵羊以及需要作为饲养动物展示的兔子，优先复用现有 `src/livestock` 的公共能力：

- 动物工坊中的地面动物选择
- 单只真实骨骼采样
- 三档作者 LOD
- Pose Cache
- 1／10／50／100／500 群体预览
- 暂停、恢复、逐帧、时间轴、循环和末帧
- 固定与 Auto LOD
- 现有 Renderer 与生命周期

但每个物种的几何、骨架、动作、动作池、预览格距和检查仍由自己的目录拥有。不得为了减少文件数量复制或缩放已有猪、犬、猫模型，也不得新建一个通用 Quadruped 生成器。

### 地面环境动物

猴子和鹿默认视为**环境动物**，不是家畜或坐骑。

做到对应阶段时，先判断现有家畜工作台能否只通过目录语义扩展而自然承载。如果猴子的攀爬／双足姿态、鹿的野生群体展示等需求会污染家畜契约，则新增最小的环境动物预览层，而不是把特殊逻辑塞进 `src/livestock`。

本工作流当前不授权：

- 捕猎
- 驯服
- 战斗
- 攀爬 AI
- 逃跑 AI
- 群体导航
- 繁殖
- 饥饿／疲劳
- 生态种群模拟

猴子可用于寺观、园林、市井表演或城市边缘等场景；鹿优先面向园林、山林、郊野和特殊院落，不默认随机出现在普通街道。

### 鸟类

鸟类阶段不预先限定只做一种。首批优先从中国古代城市场景辨识度高、经营俯视价值高的物种中选择，例如：

- 鸽子
- 麻雀
- 燕子
- 喜鹊
- 乌鸦／鸦科
- 后续需要的水边鸟类

鸟类不能因为“也是动物”就直接套地面家畜动作。做到 A6 时应建立最小的鸟类环境预览能力，至少能表达：

- 地面停驻／跳步或行走
- 啄食
- 起飞
- 飞行
- 降落

是否需要共享鸟类骨架、飞行路径、群体惊飞和屋顶落点，必须在 A6 根据第一只鸟的真实实现决定；不得现在提前建立大而全的通用飞行动物框架。

### 鱼类

鱼类阶段服务河道、池塘、水渠和水域生命感。首批可从鲤鱼等中国城市与园林水体中容易识别的鱼类开始，再按需要扩展其他鱼。

鱼类不进入地面家畜系统，不使用陆地 LOD／接地契约。A7 开始时建立最小水生环境预览能力，重点验证：

- 单鱼轮廓
- 游动循环
- 转向时身体连续性
- 近景与经营俯视的可读性
- 小群／鱼群批次
- 水面或水体范围内的展示

当前不做捕鱼玩法、繁殖、觅食生态、水质需求、真实流体、碰撞或正式 Unity 鱼群 AI。

## 每个物种的固定接手流程

开始任何一个新动物阶段前：

1. 重新读取远端最新 `main`，不得使用聊天里的历史 SHA 覆盖并行提交。
2. 阅读根 `AGENTS.md`、`README.md`、`Documentation/工作交接.md` 和本文件。
3. 阅读最接近该物种的现有实现与专篇，但只复用系统接口，不复制错误的物种造型。
4. 在对应物种专篇中先确定：
   - 正式 ID 与中文名称
   - 使用场景
   - 轮廓特征
   - 骨架边界
   - 三档 LOD 目标
   - 正式动作列表
   - 默认日常混合池
   - 群体数量与预览格距
   - 当前明确不做范围
5. 创建独立任务分支，正常提交、PR、检查、看图和合并；禁止 force push。
6. 合并前再次读取最新 `main`，保留人物、军人、服饰、动作、坐骑和其它动物的并行修改。

## 作者模型与动画共同原则

所有新动物继续以《万户天工》的模拟经营俯视为第一观察距离：

- 优先轮廓、体态和物种辨识，不追求近景毛发微细节。
- 保持低模、闭合实体、稳定蒙皮；避免透明毛卡成为主体识别手段。
- LOD0／LOD1／LOD2 都要保留关键物种特征，不能通过突然删除头、颈、四肢或尾巴来降面。
- 不为了动作增加不必要的专用网格或骨骼。
- 有睡眠动作时默认只显式预览，除非对应阶段已经有明确的昼夜调度需求。
- 奔跑、威吓、逃逸等高强度动作是否进入日常池按物种单独决定。
- 动作必须优先保证真实播放方向、接地／水域关系、附件根部和循环连续性。

## 群体与性能边界

Web Demo 的群体用于作者验证，不等同于 Unity 正式 ECS 性能实现。

地面物种在适用时继续验证 1／10／50／100／500；鸟类和鱼类在对应阶段根据批次与可读性确定等价规模，但不得把浏览器帧率写成 Unity 性能结论。

继续优先复用共享姿态缓存和实例批次，不为每只动物创建独立 Mixer。不得因为新增物种降低旧物种的数值、缓存、Renderer 生命周期或浏览器回归门槛。

## 自动检查与视觉验收

每一阶段至少需要：

- 模型预算、有限坐标和闭合拓扑检查
- bind／inverse bind 与真实蒙皮检查
- 全部正式动作和全部 LOD 的稠密采样
- 关键附件或四肢根部不离体
- 循环首尾连续
- Pose Cache 一致性
- 适用时的 1 至 500 群体批次检查
- 实际破坏数据的故障注入
- 真实浏览器交互检查
- 真实 WebGL 关键截图

视觉阶段必须实际打开截图检查。最终回复继续区分：

- **自动检查通过**：程序与浏览器断言通过。
- **AI 已看图**：执行 AI 实际打开最终截图检查。
- **用户最终认可**：必须由用户查看结果后决定。

关键截图直接展示在对话中，不能只给 artifact、ZIP 或 Actions 链接。

## GitHub 工作流边界

继续只保留当前正式 Actions：

- Build & Core Checks
- Targeted Numeric Checks
- Manual Visual Review

新物种的检查优先扩展现有 Targeted scope 和现有动物检查入口。鸟类／鱼类阶段如果需要新脚本，可以新增脚本和 job 内步骤，但默认不增加第四条永久 workflow。

本文件只定义后续动物路线，不代表尚未开始的物种已经实现或已经进入运行时目录。
