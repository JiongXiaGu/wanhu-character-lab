# 军人与甲胄工作流

## 当前执行点：S6-6 Heavy 整体重做与三级验收

Heavy 现在进入整体重做，不再在 S6-5 候选上补丁式修形。目标是重甲步兵：厚重上甲、真正长甲裳/长战裙、完整重盔；不以骑乘兼容作为 Heavy 的造型目标。S6-5 已合入 main 的版本只作为历史审查基线。

从 S6-6 起明确分成三条验收路径，禁止把发布 Gate 套到每一次模型迭代：

| 路径 | 使用时机 | 必跑 | 明确不跑 |
|---|---|---|---|
| Fast / 作者迭代 | 每次改 Heavy 几何、轮廓、局部盔甲 | `Targeted Numeric Checks → soldier-heavy-authoring`；需要看图时 `Manual Visual Review → soldier-heavy-fast` | 动作准备、Light/Medium motion、full browser、骑乘/坐骑、全衣柜、完整发布矩阵 |
| Candidate / Heavy 候选 | 造型方向已经基本成立，准备查动作与接入 | `Targeted Numeric Checks → soldier-heavy-candidate`：静态/穿插 + Heavy motion + focused fitting browser | Light/Medium motion shard、full soldier browser、完整 motion coverage |
| Release / main Gate | 建 PR、准备合入 main，仅在候选稳定后 | PR 自动 Build & Core + Targeted 完整回归；视觉改动再跑正式 soldier visual | 不允许用 Fast/Candidate 成功冒充发布 Gate |

作者迭代阶段优先直接在任务分支提交，不必为了每个小改动创建 PR。Fast 数值通道不提取动作、不启动浏览器；Fast 视觉只生成 Heavy 正/侧/背和 Medium/Heavy 同机位对比四份真实 WebGL 证据。只有当这四张图的方向成立，才进入 Candidate。共享 rig、assembly、Recipe、motion、通用变形或 CI 本身发生变化时，不得使用 Heavy-only 快速结论替代完整回归。

Heavy 专属作者文件 `heavy-top.ts`、`heavy-skirt.ts`、`heavy-equipment.ts` 在自动 Targeted 作用域中由 soldier lane 单独拥有，不再因为位于 wardrobe 目录就自动扇出到 riding/mounts；如果同一提交还改了共享 wardrobe/runtime 文件，则共享文件仍会正常触发对应回归。

## 目标与数据所有权

军人第一视觉轴为甲装等级 `light / medium / heavy`，分别表达轻短灵活、标准正规军甲装、长甲裳/长战裙与宽厚沉稳的重步兵。驻地 `palace / frontier / city` 为第二轴，主要负责 palette 与头盔；身份只有 `soldier / captain`，只改变 headwear variant。重甲是一个中性、可染色的共享基底，不复制三份驻地专属近似甲。大轮廓和色块优先，不做魔幻巨肩。

`src/soldier/` 拥有试衣分类、配色和头盔选择；真实甲胄作者资产在 `src/character/wardrobe/assets/military/`，沿原封口和装配入口工作，不建立第二套生成器或 Renderer。首次从居民装进入驻地可应用该驻地默认套装；后续驻地切换不覆盖等级、混搭衣裤和装备。等级由实际 top + bottom 推导，混搭返回无完整等级；身份由 headwear 推导，不能独立保存第二份状态。

Recipe 保持 V5 六字段 `version / bodyType / slots / dyes / hairStyle / hairColor`，七槽位 `headwear / top / bottom / shoes / back / leftHand / rightHand`。不得加入 serviceStyle、armorClass、soldierIdentity、profession、role 或 rank。固定男女、20骨、最多双权重、inverse bind、Actor 生命周期、Renderer 数量、Mixamo/MediaPipe/GLB 链路、保存与染色协议不变。不增加肩甲骨、甲裙骨、动态肩甲或实时布料。

## 分阶段执行与停止条件

每轮只处理对应层。S6-6 明确允许 Heavy 上甲、下甲与六款重盔整体重做，但不扩 Recipe、骨架、Renderer、武器或玩法。开发期使用 Fast/Candidate/Release 三级通道；提速只能来自缩小与改动范围相符的执行面，不能删除断言、降低采样、放宽容差、增加 Heavy 豁免或伪造截图。交付必须说明当前属于哪一层，Fast/Candidate 结果不得写成 main 发布完成。

## Actions 执行与加速边界

只保留 Build & Core Checks、Targeted Numeric Checks、Manual Visual Review 三条永久 workflow，不新增第四条“快速工作流”。快速通道通过现有 workflow 的显式 scope 完成。

### Fast / 作者迭代

- 在任务分支上手动运行 Targeted Numeric Checks，选择 `soldier-heavy-authoring`。
- 该 scope 只执行 `scripts/check-soldier-heavy-authoring.ts`：Heavy 拓扑、闭合/非流形、有限坐标、骨权重、预算、男女×三 palette、轮廓与故障反例。
- 不执行 `prepare-motion`，不执行 Light/Medium/Heavy 动作矩阵，不安装浏览器，不运行 riding/mounts/wardrobe 全套。
- 需要看图时手动运行 Manual Visual Review，选择 `soldier-heavy-fast`。它跳过动作提取，只 build 当前精确 SHA 并用原 WebGL Canvas 生成 `heavy-front.png`、`heavy-side.png`、`heavy-back.png`、`medium-vs-heavy-front.png`。
- Fast 图只回答“造型方向是否成立”，不回答动作、保存恢复、完整交互或发布安全性。

### Candidate / Heavy 候选

- 造型通过 Fast 后手动运行 Targeted Numeric Checks，选择 `soldier-heavy-candidate`。
- 保留 soldier 静态合同和完整下身穿插；动作只运行 Heavy shard；浏览器只运行 focused fitting。
- 不运行 Light/Medium motion shard，不运行 full soldier browser，不做三 shard coverage 汇总。
- Candidate 用来发现 Heavy 动作/接入问题；通过后再建立或更新正式 PR。

### Release / main Gate

- PR 自动行为保持完整：Build & Core Checks + Targeted Numeric Checks 按真实变更范围运行。
- Soldier 发布回归仍使用 light/medium/heavy 三 motion shard、focused/full browser 和完整 coverage gate；共享运行时变动会正常扩大 scope。
- Heavy 专属 `heavy-top.ts / heavy-skirt.ts / heavy-equipment.ts` 不再仅因 wardrobe 目录归属触发 riding/mounts；soldier lane 已覆盖其作者、装配、动作和下身穿插。若同时修改共享 wardrobe/rig/riding 文件，相关回归仍会触发。
- Manual Visual Review 继续按需：Fast 使用 `soldier-heavy-fast`；正式发布视觉证据使用 `soldier` / `[soldier-visual]`，不能拿四张 Fast 图替代发布截图矩阵。

缓存只保存动作提取输入，不缓存测试结果。完整 Gate 的动作源键/中点、原穿插容差、故障注入、V5/inverse bind 和相机约束保持不变。

`node scripts/check-ci-graph.mjs` 随 Build 验证：仍只有三条永久 workflow、Fast 不调用动作准备、Candidate 只有 Heavy motion/focused browser、Release 保留三 shard + coverage，并防止 Heavy 作者文件重新扇出到无关 riding 路径。

### Actions 查询纪律

Fast、Candidate、Release 都遵循同一原则：Actions 只负责验收，不能成为高频查询主循环；但 **CI 运行中也不能成为提前结束 Heavy 任务的理由**。

- 触发后先确认目标 SHA 与 workflow 正常启动，不按 workflow → jobs → steps 反复查询。
- runner 工作期间继续模型修复、作者检查、文档同步、截图整理、PR/合并准备等独立工作。
- Fast 阶段只关心快速作者结果；失败就回到 Heavy 几何，不等待或启动无关 Release 矩阵。
- Candidate 阶段只处理 Heavy 静态/完整下身穿插、Heavy motion 和 focused fitting；通过前不扩大到 Light/Medium/full browser。
- Release 是真正的 main Gate。若完整 Gate 已经是唯一剩余依赖，使用单次 watch / 持续等待优先；无此能力时低频检查。run 仍为 queued / in_progress 不得直接写“本轮结束”。
- 只有 workflow 达到自身 timeout、连续约 20 分钟没有状态进展且没有其它工作可推进、工具/权限硬阻塞，或用户要求停止时，才允许交回未完成状态。
- failure / cancelled / action_required 时读取真实失败 step/log，修真实原因后继续本轮；不删除检查、不加 Heavy exception、不降低动作/穿插门槛。
- 修改 workflow / package / shared runtime 时完整 Release 回归仍合理，但只为发布验证服务，不恢复每次 Heavy 小改都跑全量矩阵。

这条纪律的目标是同时避免两种错误：一是盯 Actions 造成大量无效查询，二是因为不盯 Actions 就把本来应该完成的 Heavy 交付拆成多个半成品轮次。

## 提交与最终发布

S6-6 作者阶段不要求每个小批建立 PR。先在任务分支完成 Fast 循环；造型方向稳定后运行 Candidate；只有 Candidate 成立才进入正式 PR。PR 的自动完整 Gate 仍是合并前证据，Fast/Candidate 的成功不能替代它。

用户美术认可与自动检查始终分开。Fast 四图、Candidate 动作图、正式发布截图必须标明各自 SHA 和 scope；Manual skipped 不是视觉 success，本地结果不是 Actions 结果，旧候选成功不能冒充新提交通过。

最终合并前重新读取 main 并保留并行修改，使用 expected head SHA 正常 merge，不强推；合并后按实际改动范围复检 main。若只是文档收尾且运行时代码与受测候选完全一致，明确记录差异，不重复无意义的视觉矩阵。

本轮不做新武器、刀盾/弓弩兵、背旗、披风、将军、多级军阶、职业生成器、战斗AI、伤害、阵型、ECS军队、Root Motion、Foot IK、万人GPU Crowd或Unity正式士兵玩法。历史S0至S5和被否定几何查Git历史，不恢复运行时兼容。
